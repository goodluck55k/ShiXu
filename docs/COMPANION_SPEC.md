## 1. 职责与原则

### 1.1 职责边界

| 关注点 | 负责 | 不负责 |
| --- | --- | --- |
| 情绪确认 | 用户确认或纠正九类情绪；正式保存后形成一条情绪日记 | 不直接决定性格描述、行为或离线事件 |
| 性格评分 | 按配置把已保存情绪转换为五维贡献；维护贡献账本、规则版本与主导性格 | 不读取 UI、不决定具体动作、不调用模型 |
| 主导性格 | 从五维分数中确定当前主导维度；提供稳定、确定性的切换规则 | 不向用户展示内部分数或排名 |
| 行为选择 | 按主导性格、行为类别、触发条件与权重选择动作 | 不修改性格、不写存档、不产生奖励 |
| 离线生活 | 按最后一次有效活动与主导性格生成有限的离线事件 | 不改变五维分数、不伪造情绪日记、不惩罚用户 |
| 久别重逢 | 判断长期未访问、生成一次问候并记录已触发状态 | 不把回答当作情绪日记、不改性格分数、不调用实时大模型 |
| 角色展示 | 读取快照/行为决定并渲染表情、姿态、动画 | 不修改性格、不触发评分、不重新抽取行为 |

### 1.2 设计原则

1. **性格是隐藏的行为倾向**，不是当前心情的复制，不是人格测评，也不是用户的心理健康指标。
2. 五维分数独立累计；不得把五维归一化，不得强制总和为固定值，不得用一维的升降抵消另一维。
3. 用户只能通过小白人的行为、状态和自然语言描述感知性格；界面不得出现五维分数、排名、进度条、雷达图或百分比。
4. 只有用户正式保存的情绪日记才产生性格贡献。AI 只辅助识别情绪，不直接改变分数或行为。
5. 所有正式状态变化经 `applyGameEvent`；评分、行为、离线、重逢均由带版本号的配置和确定性规则驱动，不依赖隐式 `Date.now()`、`Math.random()` 或网络。
6. 不惩罚用户：没有饥饿、掉级、死亡、断签损失、离线衰减、长期不登录惩罚，也不因负面情绪施加表外扣减、删除历史或额外惩罚；评分表内的负向贡献属于正常规则变化。
7. 害怕、低落是有效性格倾向，不是错误状态、失败状态或惩罚机制；不得用“修复”“治愈”“纠正性格”描述它们。

## 2. 五维性格

### 2.1 维度定义（已确认）

| 维度 ID | 中文名 | 行为倾向 | 说明 |
| --- | --- | --- | --- |
| `gentleness` | 温柔 | 轻声、照顾、安静陪伴 | 对他人的柔和倾向 |
| `curiosity` | 好奇 | 观察、探索、靠近新事物 | 对未知的兴趣 |
| `cheerfulness` | 开朗 | 活跃、外放、主动互动 | 外显的活力与社交倾向 |
| `fearfulness` | 害怕 | 谨慎、退缩、寻找熟悉角落 | 有效的自我保护倾向，不是错误状态 |
| `low_mood` | 低落 | 安静、迟缓、独处、沉思 | 游戏内的长期低落倾向，不是抑郁症诊断 |

补充约束（已确认）：

- 五维独立保存、独立更新；“温柔高”不意味着“害怕必须低”，不得建立互斥或此消彼长规则。
- 「害怕」和「低落」是有效性格倾向。用户记录焦虑、悲伤等情绪不会让小白人“坏掉”，也不构成对用户的惩罚。
- 「低落」只描述虚构角色在游戏中的长期倾向。不得根据评分推断用户患有抑郁症、焦虑症或其他心理疾病，不得输出诊断、治疗或医疗建议。
- 五维没有“正确值”或“培养路线”；用户不能手动加点、选择维度或查看精确分数。

### 2.2 性格来源

只有**用户确认并正式保存**的情绪日记才产生性格贡献。手动选择与 AI 建议使用同一张基础评分表和同一套结算规则。

- AI 标签仅作为基础评分的输入；AI 不得直接写分数、决定主导性格、选择行为、生成离线事件或触发重逢。
- 用户纠正情绪时，按替换规则重算该条贡献，不重复累计。
- 当前情绪可以短暂影响表情和动作幅度，但不得覆盖主导性格的长期行为规则；情绪不是性格。
- 离线生活、重逢回答、页面浏览、点击互动、刷新本身都不产生性格贡献。

### 2.5 候选参数与确定性结算

#### 2.5.1 候选参数

| 参数 | 候选值 | 状态 | 说明 |
| --- | ---: | --- | --- |
| 初始分 `initialScore` | 50 | 候选 | 每个维度独立初始值；迁移后的新五维也从此值开始 |
| 下限 `minScore` | 20 | 候选 | 存档级不变量；不得由单条日记突破 |
| 上限 `maxScore` | 80 | 候选 | 存档级不变量；不得由单条日记突破 |
| 单次单维上限 `perSaveCap` | 3 | 候选 | 单条日记对单个维度的最大绝对变化 |
| 每日单维上限 `dailyNetCap` | 4 | 候选 | 同一 `dayKey` 内单个维度的净变化上限 |
| 强度系数 `intensityFactor` | `<0.35 → 0.5`；`0.35–0.7 → 1.0`；`>0.7 → 1.5` | 候选 | 区间边界采用 `[0, 0.35)`、`[0.35, 0.7]`、`(0.7, 1]`，避免 0.35/0.7 落在两个区间 |
| 惯性系数 `roomFactor` | 公式待确认；未确认前取 `1.0` | 待确认 | 用于接近上下限时减小变化；不得自行发明新公式并写成定稿 |
| 描述分带 | `≤42` / `43–57` / `≥58` | 候选 | 只影响自然语言描述，不影响分数 |
| 主导并列顺序 | 温柔 → 好奇 → 开朗 → 害怕 → 低落 | 候选 | 只用于并列取舍，不代表维度高低 |

> **代码差异必须显式处理**：当前 `src/domain/companion.ts` 的 `PERSONALITY_PARAMS.dailyNetCap` 为 `6`，与本文候选值 `4` 不一致。阶段二实现时必须二选一：按本文改为 `4`，或由用户明确确认继续使用 `6`。不得在不说明的情况下保留 `6` 并声称符合本文。

#### 2.5.2 单条贡献计算

对每个维度独立计算，顺序固定：

1. 取基础值 `base`（2.3 表）。
2. 乘情绪强度系数 `intensityFactor`。
3. 乘惯性系数 `roomFactor`（未确认前为 `1.0`）。
4. 按“半值远离零”取整：`roundHalfAwayFromZero(x) = sign(x) * round(abs(x))`；不得使用银行家舍入。
5. 单维裁剪到 `[-perSaveCap, +perSaveCap]`。
6. 计算该 `dayKey` 已保存贡献的当前净值 `dayDeltas`；本步骤只约束**当前版本的新写入**，不回算历史。设 `lower = min(0, max(-perSaveCap, -dailyNetCap - dayDeltas))`、`upper = max(0, min(perSaveCap, dailyNetCap - dayDeltas))`，将 `x` 裁剪到 `[lower, upper]`。
   - 若历史合计未越界（`-dailyNetCap ≤ dayDeltas ≤ dailyNetCap`），裁剪后必须满足 `-dailyNetCap ≤ dayDeltas + x ≤ dailyNetCap`。
   - 若历史合计已越界，新贡献只允许 `0`，或使 `|dayDeltas + x| < |dayDeltas|`；结果允许仍越界，但不得扩大绝对值。
   - 正负方向对称。示例：历史上限 `dailyNetCap = 4`、历史合计 `+6` 时，新增 `-1` 得 `+5` 允许，新增 `+1` 得 `+7` 拒绝；历史合计 `-6` 时，新增 `+1` 得 `-5` 允许，新增 `-1` 得 `-7` 拒绝。
7. 保存整数增量；`0` 也保留为显式 `0`，便于审计与纠正。

派生分数不单独保存：

```text
score(d) = clamp(initialScore + Σ contribution.deltas[d], minScore, maxScore)
```

其中求和只包含已保存的贡献；`clamp` 是存档级保护，不替代单次/每日上限。

#### 2.5.3 确定性与舍入契约

- 同一份存档、同一规则版本、同一组已保存日记，必须得到同一组贡献和同一组派生分数。
- 结算顺序以 `dayKey` 内已保存贡献的账本顺序为准；纠正只替换目标条目，不重排其他条目。
- 每日上限在写入时应用；读取时不得再次改变贡献。
- 所有增量必须是整数；分数可使用整数派生，不引入浮点累积误差。
- 规则版本升级不得重算旧贡献；旧贡献按自己的 `rulesVersion` 解释。
- 上述规则中，初始分、上下限、单次/每日上限、强度分带均为候选；在用户确认前按候选值实现时，PR 必须标注「参数待验收」。

### 2.6 贡献账本与纠正

`PersonalityContribution` 每条至少包含：

```ts
{
  dayKey: string;          // 保存时的本地自然日
  label: EmotionLabel;     // 正式九类枚举
  entryRevision: number;   // 结算时对应日记修订号
  deltas: Record<DimensionId, number>;
  rulesVersion: string;    // 该条贡献使用的规则版本
}
```

结算规则：

1. 只有正式保存成功的日记才写入贡献；保存失败不得留下半条贡献。
2. 同一 `entryId` 最多一条贡献；重复事件、刷新、重试不得重复计分。
3. `CONFIRM_ENTRY` 使用当前规则版本和新日记的 `dayKey` 创建贡献。
4. `CORRECT_EMOTION` 必须找到原贡献，使用**原贡献的 `dayKey` 和 `rulesVersion`**，先减去旧贡献，再按该版本剩余每日额度重算并替换；余量按该 `dayKey` 下所有已保存贡献的实际合计计算（不区分版本），但上限参数取原贡献版本；重算的裁剪与超限规则按 2.5.2 执行，若扣除旧贡献后该日合计仍越界（绝对值超过原版本上限），新贡献只允许 0 或使合计绝对值严格减小。不得按新日期、新版本或当前 `dailyNetCap` 重算，不得追补其他日期，也不得改动其他贡献。
5. 找不到原贡献或找不到该 `rulesVersion` 的配置时，拒绝纠正并保留原状态；不得猜测旧参数。
6. 正文编辑不改变情绪贡献；只有情绪纠正才替换贡献。
7. 纠正不得回退其他日期已形成的成长，也不得批量重算历史。
8. 若旧条目没有贡献（例如迁移前数据），纠正只更新当前情绪/修订，不补记历史贡献；这是“迁移不追溯”规则的一部分，不属于待确认事项。

### 2.7 派生、查询与主导性格

只读接口至少包括：

- `derivePersonality(state, config): PersonalitySnapshot`：汇总贡献、裁剪上下限、计算主导性格。
- `getDimensionScore(snapshot, dimensionId): number`：只读查询单个维度。
- `describeDominantPersonality(snapshot, config): string`：只返回当前主导性格的自然语言描述。
- `resolveDominant(scores, previousDominantId, priorityOrder): DimensionId`：确定性主导判定。

主导判定（**已确认“最高分主导”，具体并列规则为候选**）：

1. 取五维派生分数的最高分维度作为主导性格。
2. 首次判定或 `dominantId` 缺失时，按配置顺序 `gentleness → curiosity → cheerfulness → fearfulness → low_mood` 取并列中的第一个。
3. 之后 `dominantId` 持久化在 `PersonalityState` 中；只有其他维度**严格高于**当前主导分数时才切换。
4. 挑战者之间并列时，按上述固定顺序取第一个；当前主导与挑战者并列时保留当前主导。
5. 不允许使用随机数、时间或 UI 状态决定主导；不得设计“每次刷新重新选最高分”的无状态实现，否则并列时会抖动。
6. 主导切换只改变行为风格和展示描述，不修改五维分数，不产生奖励或惩罚。

展示约束（已确认）：

- 只表现当前主导性格的行为风格；其他维度不直接参与主要行为选择。
- 界面只展示主导性格的自然语言描述与行为差异；不展示五维分数、排名、进度、雷达图或“距离下一阶段还差多少”。
- 即时情绪只影响表情、动作幅度等短时表现，不得覆盖主导性格的长期行为池。

### 2.8 描述文案

- 每个维度至少三段自然语言描述：`≤42`、`43–57`、`≥58`（候选分带）。
- 描述只用于当前主导维度；非主导维度的描述可用于内部调试，但不进入用户界面。
- 文案不得使用诊断、治疗、治愈、人格缺陷、失败、惩罚等措辞；不得暗示用户“应该”产生某种情绪。
- 文案由配置提供并带版本号；不得散落在 React 组件中。

### 2.9 规则版本与配置

- 新五维规则版本：`personality-v2`（候选命名，实施前可由用户确认）。
- 已实现的 `companion-v1` 三维账本只作为历史兼容；不得继续扩张三维规则。
- 文档中旧的五维草案 `personality-v1`（`liveliness` / `courage` / `gentleness` / `sensitivity` / `curiosity`）从未在 `main` 实现，也没有持久化贡献；不得把它当作已有数据迁移来源。
- 配置至少包含：维度顺序、初始/上下限、单次/每日上限、九类情绪基础表、强度分带、惯性配置、描述分带、主导并列顺序、规则版本。
- 旧规则配置必须保留，供历史贡献解释和纠正使用；不得因为升级而删除旧配置。
- 读取旧贡献时按贡献自身 `rulesVersion` 验证：单条 `deltas` 不超该版本 `perSaveCap`；同一 `dayKey` 内若全部贡献同版本，每个维度的合计不超该版本 `dailyNetCap`；同日混合版本时只逐条校验，不按当前版本重新聚合拒绝。
- 新写入只受 `PersonalityState.rulesVersion` 的 `perSaveCap` / `dailyNetCap` 约束；不得用新规则重算旧贡献。历史日合计在 `[-dailyNetCap, dailyNetCap]` 内时，写入后不得越界；历史合计已越界（`|dayDeltas| > dailyNetCap`）时，只允许 0 或使该维度合计绝对值严格减小（结果可仍越界）。
- 旧版本配置缺失时，保留原贡献并标记不可纠正；纠正请求拒绝，不得猜测旧参数或静默改写存档。
- 修改已确认规则或候选参数必须由用户决定；实现者只能报告差异、影响和建议。

### 2.10 验收要点

1. 五个维度 ID 与中文名符合 2.1，且五维独立累计。
2. 九类情绪枚举未被增删改名；候选表可配置、可替换、带规则版本。
3. 单次上限、每日上限、取整、纠正替换、每日剩余额度均有确定性测试或可复现验证。
4. 纠正使用原 `dayKey` + 原 `rulesVersion`；缺配置时拒绝而不是猜测。
5. 主导性格持久化；并列不抖动；只有严格超过才切换。
6. 界面不出现五维分数/排名；只展示主导描述和行为。
7. 旧三维账本迁移到 `legacy`，日记、历史、纠正记录不丢失；新五维从初始值开始。
8. AI 不写分数、不决定主导、不选择行为。

## 3. 主导性格行为库

### 3.1 行为类别（已确认分离）

| 类别 | 作用 | 是否由主导性格决定 | 示例 |
| --- | --- | --- | --- |
| `ambient` 普通待机 | 没有明显性格事件时的基础呼吸、张望 | 否 | `idle_breathe`、`idle_glance` |
| `dominant` 主导性格行为 | 表现当前主导性格的日常动作 | 是，只读 `dominantId` | 见 3.2 |
| `special` 特殊行为 | 连续低落满足条件后的颓废行为 | 是，但需额外条件 | `drink`、`smoke` |
| `interaction` 用户主动互动 | 对呼唤、抚摸、观察的即时回应 | 否，但可带主导语气/幅度 | `respond_call`、`respond_pat`、`respond_observe` |

这四类在配置、选择逻辑和验收中必须分开；不得把特殊行为混进主导行为池，也不得把互动反应写成长期行为。

### 3.2 主导行为库（已确认候选动作）

- V1 允许简化动画、SVG 变形或占位表现，不要求提前完成正式美术资源；但行为 ID 与语义必须稳定。
- 行为选择只读取 `dominantId` 对应的池；其他维度分数不得参与主要行为加权。

### 3.3 行为选择上下文与算法

`BehaviorContext` 至少包含：

```ts
{
  personality: PersonalitySnapshot; // 只读；使用 dominantId
  emotion: EmotionReading | null;   // 只用于表情/幅度，不参与主池选择
  interaction: InteractionEvent | null;
  specialEligible: boolean;         // 由应用层只读计算，行为引擎不读日记
  dayKey: string;
  timeBand: TimeBand;               // 只影响 ambient 权重
  sequence: number;
  seed: number;
  lastBehaviorId: BehaviorId | null;
  consecutiveCount: number;
}
```

选择顺序固定：

1. 有 `interaction` → 选对应的 `interaction` 行为，结束。
2. 若 `specialEligible === true` 且 `dominantId === "low_mood"`，按 `specialProbability` 做确定性抽样；命中则从 `special` 池按权重选择。
3. 若没有主导性格，或按 `ambientShare` 确定性抽样命中，从 `ambient` 池选择。
4. 否则从“当前 `dominantId` 对应的主导行为池”按权重选择。
5. 若结果与 `lastBehaviorId` 相同且 `consecutiveCount >= maxConsecutive`，按配置顺序轮换到同池下一个行为；不得连续超过上限。
6. 权重抽样必须使用显式 `seed + sequence + dayKey` 的确定性 PRNG；相同上下文必须得到相同结果。

候选参数：

| 参数 | 候选值 | 说明 |
| --- | ---: | --- |
| `ambientShare` | 0.15 | 普通待机占比 |
| `specialProbability` | 0.15 | 满足条件时特殊行为命中概率；不是必然触发 |
| `maxConsecutive` | 2 | 同一行为最大连续次数 |
| `minShare` | 0.05 | 同池行为最低出现份额（长期调度约束） |
| `tickIntervalMs` | 20–40 秒 | 行为调度间隔；由应用层显式计时 |
| `interactionDurationMs` | 2.5–4 秒 | 互动反应时长 |
| `saveFeedbackDurationMs` | 3000 毫秒 | 保存后一次性反馈时长 |
| `emotionExpressionDurationMs` | 3000 毫秒 | 即时情绪表情/幅度的运行时有效期；到期回基础表情 |

### 3.4 即时情绪与行为的关系

- 情绪只映射到表情、眼神、动作幅度、速度等短时表现；不得改变主导行为池，也不得把“当前悲伤”直接变成长期低落。
- 表情可以在互动或事件后短暂变化，随后回到主导性格的基线；不得覆盖主导性格的长期行为规则。
- 即时情绪只在保存成功后的运行时有效期（`emotionExpressionDurationMs`，候选 3000 毫秒，待验收）内影响表情与幅度；到期回到主导行为配置的基础表情，刷新页面不重新激活已结束的即时情绪表现或反馈。该有效期不改变已保存情绪、日记与五维贡献。
- 不得用 AI 生成动作、姿态或行为 ID；行为只能来自配置枚举。

### 3.5 连续低落特殊行为（条件已确认，判定细节待确认）

只有**同时满足**以下两个条件，才允许触发低落专属特殊行为：

1. `low_mood` 是当前五维最高分的主导性格。
2. 用户连续超过 3 个自然日记录低落情绪，即第 4 天开始符合条件；第 4 天是否必须当天也保存低落记录，存在两种待确认语义，见 3.5.1。

行为候选：`drink`（喝酒）、`smoke`（抽烟）等虚构角色的颓废行为。要求（已确认）：

- 不是必然触发；由配置概率决定，未命中时走正常主导行为。
- 不产生奖励、成长加成、额外性格积分或资源。
- 不把喝酒、抽烟表达为改善情绪的方法；不得出现鼓励、疗效或“喝了就好了”的文案。
- 主导性格不再是 `low_mood` 时停止触发。
- 连续低落中断后停止触发。
- 没有记录的日期不得自动算作低落日。
- 机制只作用于虚构角色，不用于判断用户的心理健康状况。

**关键未确认项**：九类情绪中没有名为「低落」的枚举。哪些情绪标签计入“低落日”尚未确认；候选仅 `sadness`，是否纳入 `tired`、`mixed` 或按 `low_mood` 维度判定均待确认。因此：

- 配置项 `specialBehaviorEnabled` 默认 `false`；在用户确认前，阶段三只实现机制和测试入口，不得在正式流程触发。
- `lowMoodEmotionLabels` 候选为 `["sadness"]`，但不得写成已确认产品规则。
- 连续天数判定、同一天多条记录、纠正、跨日、时区的候选规则见 3.5.1；全部标记待确认，不得自行定稿。

#### 3.5.1 连续天数候选判定（待确认）

以下只是可实现的候选契约，用户确认前不得作为正式产品规则宣传：

- 一个自然日“计为低落日”当且仅当该日至少有一条已保存且未被纠正掉的情绪日记，其正式标签属于 `lowMoodEmotionLabels`；同一天多条只计一天。
- 纠正后按当前有效情绪重算；若该日已无符合标签的条目，则该日不再计为低落日，连续可能中断。
- 无记录的自然日直接中断连续，不自动补成低落日。
- `dayKey` 在保存时按本地自然日固定；之后修改系统时区不回写历史 `dayKey`。
- **第 4 天语义存在两种解释，均未确认，不得把任一种写成已确认产品规则：**
  - 语义 A（当前候选实现）：截至昨日已连续 3 个低落日，第 4 天零点起即具备资格；第 4 天尚未保存任何日记时也可触发。
  - 语义 B（更贴近“连续超过 3 个自然日记录”的字面）：第 4 天也必须至少保存一条低落日记，才具备资格；当天首次低落保存前不触发。
- 两者差异：A 可能在用户第 4 天尚未记录时出现特殊行为，B 会把触发推迟到第 4 天首次低落保存后。它们对“第 4 天开始符合条件”的解释不同，必须由用户确认。
- 确认前：`specialBehaviorEnabled` 保持 `false`；阶段三只实现机制与测试入口，不接入正式触发。不得用任一语义作为默认产品行为。
- 候选值 `streakDaysRequired = 3`（即最早第 4 天）；概率、行为权重均可配置。

### 3.6 行为调度与渲染边界

- 行为调度由应用层显式计时；页面隐藏时暂停调度与动画，恢复后重新读取状态，不补算隐藏期间的连续行为。
- 同一时刻只有一个主要行为；互动可以短暂打断主导行为，结束后回到主导池。
- 行为选择是纯函数，不写快照；`CharacterRenderer` 只消费 `BehaviorDecision` / `CharacterView`。
- 关闭网页不运行后台 Agent；离线生活由下次打开时的确定性生成器处理（见第 4 节），不在关闭期间持续推进。

### 3.7 验收要点

1. 五类主导行为池与四类行为类别可配置、可区分。
2. 主要行为只由 `dominantId` 决定；其他维度不参与主池权重。
3. 即时情绪只影响表情/幅度，不改变主导行为池。
4. 同一上下文、同一种子得到同一行为；连续次数不超过上限。
5. 特殊行为默认关闭；只有两个条件同时满足且配置开启时才可能触发，未命中时不触发。
6. 行为选择不修改性格、不写存档、不发奖励。
7. 页面隐藏暂停；关闭网页不运行后台 Agent。

## 4. 离线自主生活

### 4.1 目标（已确认）

用户离开 ShiXu 后，小白人仍然拥有自己的生活。再次打开时，系统按**最后一次有效活动**与当前主导性格，生成有限数量的离线生活事件，让用户感到角色在“过自己的日子”，而不是被惩罚或停滞。

### 4.2 离线活动库（已确认候选内容）

| 主导性格 | 离线活动 |
| --- | --- |
| 温柔 `gentleness` | 整理房间、照顾植物、安静休息 |
| 好奇 `curiosity` | 探索房间、观察新事物、收集发现 |
| 开朗 `cheerfulness` | 玩耍、跳舞、尝试游戏 |
| 害怕 `fearfulness` | 待在熟悉角落、小心探索 |
| 低落 `low_mood` | 发呆、睡觉、靠窗沉思 |

活动必须配置驱动；V1 可用文字 + 简单图标/占位表现，不要求正式动画。

### 4.3 状态与配置

```ts
OfflineLifeState {
  lastVisitAt: number | null;       // 上次成功会话启动的时间
  lastActiveAt: number | null;      // 最后一次确认活动；离线/重逢基准
  lastWindowStart: number | null;   // 上次处理的离线窗口起点，用于幂等
  events: OfflineLifeEvent[];       // 有上限的历史事件
}

OfflineLifeEvent {
  id: string;                       // offline:<windowStart>:<index>
  windowStart: number;
  occurredAt: number;
  dominantId: DimensionId;
  activityId: string;
  text: string;
}
```

候选配置：`minAbsenceMs = 30 分钟`；`eventIntervalMs = 90 分钟`；`maxEventsPerWindow = 6`；`maxStoredEvents = 20`；`rulesVersion = "offline-life-v1"`。

### 4.4 生成算法（确定性）

1. 读取 `lastActiveAt`、`lastVisitAt`、`now`、当前 `dominantId`；计算 `baseline = lastActiveAt ?? lastVisitAt`。
2. 若 `baseline === null`（首次使用或刚迁移），不生成事件；把本次访问记为起点，避免伪造“过去的生活”。
3. 计算 `absence = now - baseline`；若 `absence < minAbsenceMs`，不生成事件，窗口起点记为 `baseline`。
4. 否则事件数 `n = min(maxEventsPerWindow, max(1, floor(absence / eventIntervalMs)))`。
5. 第 `i` 个事件时间取 `baseline + eventIntervalMs * (i + 1)`，若超过 `now` 则裁到 `now`；同一窗口内保持升序。
6. 每个事件从当前 `dominantId` 的活动池按权重选择；随机源必须由 `hash(windowStart, dominantId, rulesVersion, index)` 派生，禁止 `Math.random()`。
7. 返回事件、`windowStart = baseline`、`nextLastVisitAt = now`、`nextLastActiveAt = now`。
8. 用户再次打开时，`applyGameEvent(SESSION_STARTED)` 原子写入事件与新的 `lastVisitAt` / `lastActiveAt`。

活动 checkpoint：
- 页面隐藏、`pagehide`、刷新前提交 `ACTIVITY_CHECKPOINT`；可见期间的周期性 checkpoint 最多每 5 分钟一次，避免高频写盘。任何正式保存成功后也在同一 `applyGameEvent` 中顺带更新 `lastActiveAt`。不得按行为 tick 或动画帧写盘。
- 存在未解决的 pending 日记操作（保存失败后保留的待重试事件）时，暂停正式 checkpoint 写入，直到该 pending 成功提交或被明确取消。否则 checkpoint 推进 `revision` 会使 `retrySave` 冻结的 `expectedRevision` 失效，把本标签页自己的 checkpoint 误判为跨标签页冲突。pending 解决/取消后 checkpoint 恢复；重试复用冻结的 `eventId/entryId/now/dayKey/正文/情绪`，不重算。跨标签页冲突保护与救援/降级语义不变，不引入新的高频写盘。
- 同一标签页可用 `sessionStorage` 保存救援时间戳，仅用于避免刷新/同标签页恢复被误判为离线；它不是正式存档，不得替代 `StoragePort`。
- 直接关闭且 checkpoint 成功时，下一窗口从关闭前最后活动开始；checkpoint 失败时，降级为最后一次成功的 `lastActiveAt`（或救援值）。该降级可能把未 checkpoint 的在线时长计入离线，但不会少算，也不会在保存失败时展示离线事件。
- 浏览器崩溃、隐私模式禁用存储等情况无法精确捕捉关闭时间，按上述降级处理；不得引入后台 Agent、服务器心跳或高频写盘来追求精确。

### 4.5 幂等、持久化与失败处理

- 同一次离线窗口最多生成一次；`eventId = session:<windowStart ?? "first">` 与 `lastWindowStart` 双重保护。
- 事件 `id` 确定性生成；写入时按 `id` 去重，重复应用不追加。
- `ACTIVITY_CHECKPOINT` 只把 `lastActiveAt` 单调更新为 `max(旧值, at)`；重复、乱序或重放无副作用，不写 `appliedEventIds`、不写回忆。
- 只有存档成功后才更新正式 `lastVisitAt` / `lastActiveAt`；保存失败时保持旧值，下次打开会重新生成同一窗口的相同事件，不得出现重复或半写状态。
- 离线事件只追加到有上限的历史列表，超出 `maxStoredEvents` 时从最旧事件裁剪；裁剪不影响幂等键。
- 不通过伪造情绪日记来“解释”离线生活；离线模块不写 `entries`、不写性格贡献。

### 4.6 边界（已确认）

- 离线生活不改变五维性格分数。
- 用户长时间不登录，不因此增加 `low_mood`，也不减少任何维度。
- 不因离线惩罚用户：不掉资源、不掉饰品、不掉装扮、不掉已形成的成长。
- 不自动丢失饰品、装扮或其他资源；V1 饰品系统本来就不实现。
- V1 不要求后台持续运行 Agent；只在再次打开时生成有限事件。
- 离线生活模块与性格评分模块独立：离线模块只读 `dominantId`，不读贡献账本，不写分数。

### 4.7 验收要点

1. 首次/迁移存档不生成虚假历史事件。
2. 同一窗口重复打开不重复生成；保存失败后重试仍不重复。
3. 离线事件数量有上限，时间升序，活动属于当前主导性格。
4. 离线前后五维分数完全不变；长时间离线不增加 `low_mood`。
5. 不写日记、不发奖励、不掉资源。
6. 页面刷新/重开不出现“后台持续生活”的假象；事件只在打开时生成。

## 5. 久别重逢

### 5.1 触发条件（阈值候选）

- 候选阈值：`absence > 3 天`（严格大于 72 小时）；`reunion-v1` 配置化，可调整。
- `absence = now - (lastActiveAt ?? lastVisitAt)`；用户重新打开 ShiXu 时，在更新 `lastVisitAt` / `lastActiveAt` 之前判断。
- 同标签页刷新可用 `sessionStorage` 救援时间戳抬高判定基准（`max(baseline, rescue)`），只影响是否缺席、不改变离线窗口起点，避免刷新被误判为长期离线。
- 同一次离线窗口只触发一次：`reunion.lastTriggeredWindowStart` 记录已触发的窗口起点（即 `baseline`）。
- 触发后必须**先成功保存** `SESSION_STARTED`（含 `reunionTriggered: true`），再展示问候；保存失败不展示，避免刷新重复。

### 5.2 问候内容

基础问句固定为：

> 最近过得还好吗？

根据当前主导性格，可使用不同的语气和生活经历描述。以下为候选模板，实施前需用户确认文案：

| 主导性格 | 候选语气/内容 |
| --- | --- |
| 温柔 | 轻声问候，提到整理房间/照顾植物，不追问 |
| 好奇 | 提到探索到的新东西，邀请用户一起看看 |
| 开朗 | 轻快打招呼，分享玩耍/跳舞的小事 |
| 害怕 | 小心地问候，提到熟悉的角落，不施压 |
| 低落 | 安静地问候，提到发呆/靠窗，不要求用户立刻振作 |

要求：

- 文案可配置，带 `reunion-v1` 版本；不得写死在组件里。
- 不使用责备、道德绑架或制造负罪感的文案；禁止“你终于回来了”“你都不理我”“我等了你好久”“你是不是不要我了”等表达。
- 不要求实时调用大模型生成问候；V1 使用本地模板 + 当前主导性格 + 可选离线事件。
- 问候不是情绪日记，不进入 `entries`，不产生性格贡献。

### 5.3 用户回答与跳过

- 用户可以回答，也可以跳过；两种操作都不得改变性格分数。
- 回答默认只存在于当前会话/界面，不写入正式情绪日记；只有用户后续正式保存情绪日记才产生贡献。
- 跳过不得被视为负面行为，不扣分、不触发特殊行为、不改变主导性格。
- 是否持久化“已回答/已跳过”属于待确认；V1 默认不持久化回答内容，只持久化“本次重逢已触发”。

### 5.4 验收要点

1. 超过阈值才触发；未超过不触发。
2. 同一窗口只触发一次；页面刷新不重复。
3. 保存失败不展示；保存成功后刷新不重复。
4. 回答/跳过不改分数、不写日记、不发奖励。
5. 文案不含责备/负罪感；不调用实时大模型。
6. 问候语气随主导性格变化，但基础问句保持“最近过得还好吗？”。

### 5.5 实现状态（阶段五分支）

- `src/config/reunion.ts` 提供 `REUNION_V1`：候选 `thresholdMs = 72 小时`、固定 `baseQuestion`、五主导候选 `generic` 问候与按离线 `activityId` 的具体文案。阈值与文案均待用户验收。
- `src/domain/reunion.ts` 的 `evaluateReunion` 是纯函数：基准 `lastActiveAt ?? lastVisitAt`；基准为 null、未严格超过阈值、或 `lastTriggeredWindowStart >= baseline` 时不触发；相同输入同结果；不写存档、不调用时间/随机/网络/AI。
- 触发结果只以 `SESSION_STARTED.reunionTriggered` 进入正式状态；`applyGameEvent` 仅在 `windowStart !== null` 时写 `reunion.lastTriggeredWindowStart / lastTriggeredAt`，未触发时保留原标记。
- 问候对象不进入快照；应用层仅在包含该会话事件的正式快照保存成功后，把问候放入本次运行会话的一次性展示状态。会话保存失败时问候随未提交窗口冻结，由 checkpoint 或日记保存补交成功后展示一次；回答或跳过只清运行时状态并记录已处理窗口。
- 具体生活描述只引用本次窗口真实生成并随同一事件提交的离线事件；无对应事件时回落到通用问候；不虚构经历、不要求角色依赖用户生活。

## 6. 角色展示

- `CharacterView` 至少包含 `expression`、`pose`、`animation`、`visibleLayerIds`、`effects`；阶段三可增加 `behaviorId` 便于调试。
- `CharacterRenderer` 只读快照与行为决定，不修改性格、不触发评分、不重新抽取行为。
- 角色为原创全身白色小人；V1 允许占位动画，正式视觉在阶段七由用户重新确认方向。
- 表情可以反映即时情绪，但不得覆盖主导性格的长期行为；同一时刻只有一个主要行为。

## 7. V2 饰品边界

- 饰品装扮是 V2 独立模块；V1 不实现库存、解锁、隐藏、恢复、穿戴、商城或交易。
- V1 只保留必要契约扩展点；不得把饰品字段写进五维评分、行为选择或离线生活逻辑。
- 旧存档中的装饰字段只做 `legacy` 兼容保留，不展示、不计分、不参与 V1 结算。

## 9. 与 v3 的主要差异

1. 五维从 `liveliness/courage/gentleness/sensitivity/curiosity` 改为 `gentleness/curiosity/cheerfulness/fearfulness/low_mood`。
2. 评分表、主导性格、行为库全部按新五维重写；三维 `companion-v1` 只作历史兼容。
3. 行为从“五个通用行为 + 维度权重”改为“主导行为池 + 四类行为分离”；即时情绪不再参与主行为权重。
4. 新增离线自主生活与久别重逢；删除“关闭网页完全不模拟离线生活”的旧表述，但保留“不运行后台 Agent、不惩罚、不衰减”的边界。
5. 新增 `SessionStarted` 事件、`offlineLife` / `reunion` 状态与相应持久化/幂等要求。
