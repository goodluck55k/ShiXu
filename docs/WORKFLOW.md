# GitHub 与 Codex 工作流程

本项目采用功能优先、稳定运行、最小验证的分支工作流。必须先读 [AGENTS](../AGENTS.md)，阶段和范围见 [ROADMAP](ROADMAP.md)。

## 1. 任务开始

1. 确认仓库 `goodluck55k/ShiXu`、当前分支、远端、现有文件与用户改动，不能覆盖已有有效内容。
2. 查看同任务分支和 PR 是否存在，存在则复用。先同步远端 main，再从最新 main 建对应 feature/fix/docs 分支；不在 main 直接开发。
3. 读相关规格，确认输入/输出接口与本阶段最小验收；一次性完成整个任务，不在每次编辑后重复审查。

指南任务：`docs/development-guide` 是初始指南分支，后续独立指南修订可用对应 `docs/*` 分支；先检查已有同任务分支与 PR，存在则复用。文档分支不混入产品功能代码，PR 以 main 为目标，未经用户明确授权不合并；指南 PR 不能借此启动后续功能阶段（C1 已合入，下一功能阶段为 C2），前置合入 main 后才进入依赖阶段。

## 2. Codex 实施规则

先打通一条可运行主线，再补足任务卡内必要功能。保持模块接口稳定，不无关重构，不追加未要求的基础设施和后期玩法。参考源码只借鉴已核实内容，许可边界见 [REFERENCES](REFERENCES.md)。

非关键材料、真实 API 或后续模块缺失时，用手选、明确标注 mock、本地占位素材或简化接口适配完成可运行交付。不能冒充真实联通，也不能为等待外部材料无限停止。不可运行的主要故障应修复后交付；超范围阻塞需具体记录，不以模糊的“缺证据”否定已完成范围。

当前 UI 仅作为功能验证的临时载体，处于 UI 冻结（[AGENTS](../AGENTS.md) 第 2.2 节）。功能阶段只允许「功能所需的最小呈现」：最简单的临时控件、必要状态可辨认、阻塞主流程的交互修复；禁止借功能开发重做布局、美化视觉或增加装饰性效果。正式视觉设计属于 C6 之后的独立阶段，需用户重新确认方向。

## 3. 唯一最终验证轮

| 改动 | 最小验证要求 |
| --- | --- |
| 纯指南文档 | 全部文档完成后一次检查 AGENTS.md 与 docs/ 全部指南（当前共 8 份文件，含 COMPANION_SPEC）、链接、规则一致性、分支和 diff；验收范围随 AGENTS 第 6 节文档入口表调整；不安装依赖/构建/跑产品测试 |
| 页面或组件 | 本功能主流程人工冒烟，检查新增交互与错误态 |
| 情绪接口 | 阿里云百炼 Choice / Score（或适配后的等价结构）经校验映射后可确认；失败/超限可手选保存完整原文，旧响应不覆盖新草稿或新心情；真实 API 与 mock 状态如实记录；模型/Endpoint/账号能力以核实结果为准 |
| 规则或持久化 | 本次涉及的原文/编辑不改变性格贡献、修订幂等、纠正替换不叠加、旧记录纠正不覆盖当前心情、schema 迁移保留旧数据、存档失败保留草稿及刷新恢复等少量关键案例；按当前阶段选取；C5 另检查装饰解锁/回收/再获得、回收自动取消穿戴、历史追加不丢失、重复提交不重复写历史 |
| 骨架/依赖/类型边界 | 根据实际脚本一次类型检查或构建；若必须两者都做，集中到同一轮，不逐编辑反复跑 |

不设测试数量或覆盖率门槛。只验证当前分支受影响路径，已完成且未变化的检查不重复。失败后定位修复并只复测受影响项；新变更或失败才扩大范围。真实 API 未运行、只能 mock 的部分必须明确写入 PR。测试用例仅在有实际关键行为价值时增加，不镜像实现凑数。

## 4. 提交、推送与 PR

完成后检查差异仅属于本任务，提交信息说明具体行为，例如 `docs: define ShiXu development guide` 或 `feat: add manual emotion confirmation`。提交并推送目标分支，再创建 head=任务分支、base=main 的 PR；已有 PR 更新同一个。

PR 说明以最终交付为准，包含：解决什么问题、主要行为、最小验证结果、外部限制及未验证项。纯文档 PR 明确“仅文档，无产品代码，无产品测试”。通过 GitHub 查看远端确有文件与提交，记录完整 SHA，不能只以本地 commit 当作推送成功。

审核关注稳定运行、兼容性和既定产品方向。收到打回建议，仅处理具体建议及由修复直接引起的问题，不借机无关扩展；修复推送同一分支/PR，做对应最小复测。

## 5. 合并与同步 main

未经用户明确允许，任何人机代理不得自行点击 Merge、自动合并或修改 main。创建 PR 的授权不等于合并授权。即使检查全通过也保持待审核。

用户授权合并后，确认 PR head 与当前交付一致，按授权合并；随后读取合并结果，更新本地 main，再从新的 main 开下一阶段分支。不要强推共享 main，不自行删除仍有用的任务分支。发生冲突先保留双方有效内容，解决本任务范围内冲突；产品取舍冲突明确交给用户。

## 6. 权限和异常

优先使用用户指定的操作环境，在已授权环境通过 Git 或连接器操作 GitHub。认证、写入或 PR 创建失败时报告具体环节和已完成内容；不能以文件已写入编辑框代替提交成功。

不能要求用户重复决定已明确的需求；只有缺少新的关键决定或必须由用户完成的认证时才暂停。密钥和凭证不写入仓库、PR 或聊天。

## 7. 最终汇报格式

列出新增/修改文件、关键规则、实际最小验证、未验证部分、分支、完整提交 SHA、PR 链接和“未合并”状态。文档规则落地与产品功能实现分开陈述，不能把规划目录当成现成代码。
