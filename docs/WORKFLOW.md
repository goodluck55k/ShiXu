# GitHub 与 Codex 工作流程

> 适用于 Codex、DeepSeek 及其他 AI 开发代理与人工开发者。开发目标、权限边界与产品不变量以 [AGENTS](../AGENTS.md) 为准；阶段顺序以 [ROADMAP](ROADMAP.md) 为准。

## 1. 任务开始

1. 确认仓库、当前分支、远端、默认分支与用户未提交改动；不得覆盖或删除用户改动。
2. `git fetch` 并检查是否已有同任务分支与 PR：存在则复用，不重复建分支/PR；PR 目标始终是 `main`。
3. 读取本任务相关文档：[AGENTS](../AGENTS.md)、[PRODUCT_SPEC](PRODUCT_SPEC.md)、[ARCHITECTURE](ARCHITECTURE.md)、[COMPANION_SPEC](COMPANION_SPEC.md)、[ROADMAP](ROADMAP.md)、[AI_CONTRACT](AI_CONTRACT.md)；涉及参考素材时读 [REFERENCES](REFERENCES.md)。
4. 从最新 `main` 建任务分支：功能用 `feature/<name>`，纯文档用 `docs/<name>`。指南分支只维护 `AGENTS.md` 与 `docs/`，不混入产品代码。
5. 确认本阶段在当前 `main` 的真实状态：哪些已实现、哪些只是规划。不得把未合入接口当作已有，也不得重复开发已完成功能。

### 1.1 指南任务

- `docs/development-guide` 是初始指南分支；后续指南修订可用对应 `docs/*` 分支。
- 指南分支只改规范与 `docs/` 文档，不改产品源码、不改 `main`、不自建功能分支。
- 指南 PR 同样面向 `main`；未经用户明确授权不得自行合并。
- 文档修改先完成全部内容，再做一次集中一致性检查，不按每个小编辑反复构建。

## 2. 实施规则

1. **先契约后代码**：涉及模块边界、公共类型或存档结构时，先更新 [ARCHITECTURE](ARCHITECTURE.md) 与任务卡，再实现。
2. **一张任务卡一个范围**：按 [MODULE_TASK_CARD](MODULE_TASK_CARD.md) 填写模块、输入输出、契约变更、配置版本、明确不做与最小验收；未填写不得进入审核。
3. **先打通最小闭环**：例如「日记→情绪→保存→性格派生」先跑通，再补边界与文案。
4. **禁止无关重构**：不改与任务无关的文件、不顺手美化 UI、不提前实现后续阶段或 V2。
5. **占位要标注**：缺真实 API、美术或后续模块时，使用明确标识的占位/mock，说明真实接入状态，不宣称已验证真实能力。
6. **配置与版本**：性格、主导、行为、离线、重逢、情绪映射的阈值只放在配置中；调整规则同步升版本并更新文档。
7. **权限边界**：AI 只产出情绪数据；主导判定、行为选择、离线生活与久别重逢只读本地确定性规则；组件只渲染；存储只存取；任何正式状态变化经 `applyGameEvent` 与成功保存。
8. **UI 冻结**：阶段七之前，页面只做功能必需的最小呈现，不做布局重设计、配色美化或新增装饰性组件；阶段七需用户重新确认视觉方向后解除。

## 3. 唯一最终验证轮

每个任务完成后集中做一轮与本任务相关的最小验证，不为覆盖率补测试，不按每次小编辑重复执行。

| 任务类型 | 最小验证 |
| --- | --- |
| 纯文档（本指南） | 一次检查全部指南文件：链接有效、V1/V2 范围一致、术语一致、五维/主导/离线/重逢口径一致、无旧五维名或旧三维护账被写成 V1 有效规则、无旧饰品/旧 XP 必做项、`git diff` 仅含文档 |
| 性格引擎 | 幂等重复提交、单日上限、纠正替换（含同日较早一篇）、旧版本贡献按自身 `rulesVersion` 校验且不被当前 `dailyNetCap` 误拒、迁移后旧条目纠正不补算、编辑不改贡献、v2→v3 迁移、保存失败不结算、主导严格超过才切换/并列保持、描述无数字 |
| 行为与互动 | 同上下文同结果、主导行为池、最低占比、防连续、隐藏暂停、互动不加分、即时情绪不覆盖主导行为、特殊行为双条件与默认关闭、第 4 天 A/B 语义未确认前不接入正式触发 |
| 离线生活 | 同一离线窗口幂等、刷新不重复生成且不误判离线、关闭/隐藏 checkpoint 更新 `lastActiveAt`、写入失败按最后成功值降级、离线不改五维/不增加低落、不伪造日记、保存失败不展示、首次迁移存档无离线事件 |
| 久别重逢 | 阈值内不触发、以 `lastActiveAt ?? lastVisitAt` 为基准、同一次离线只触发一次、刷新不重复、回答/跳过不改分、无责备文案、保存失败不展示 |
| 情绪 API | 手选全流程、AI 建议确认、低置信度/超时/格式错误降级、请求体与长度限制、密钥不下发 |
| 存档/迁移 | 旧版本读取、损坏与版本过新提示、空间不足、跨标签页冲突、导出/重置 |
| 页面与角色 | 主流程人工冒烟、空态/错误态、刷新恢复、窄屏与低动态设置 |

- 涉及存档完整性、迁移、幂等、成长结算的改动必须检查对应关键路径。
- 失败只复测受影响路径；修复审核问题时只处理缺陷与直接关联问题。
- 纯文档任务不安装依赖、不构建、不运行产品测试。

## 4. 提交、推送与 PR

1. 只提交本任务文件；提交信息说明「改了什么、为什么」，不写空泛描述。
2. 推送任务分支，创建面向 `main` 的 PR；已有同任务 PR 则更新，不重复创建。
3. PR 描述至少包含：
   - 关联阶段与任务卡；
   - 实际变更（文件/模块/契约）；
   - 最小验证结果与未验证部分；
   - 外部限制（无 Key、无真实账号、占位素材）；
   - 是否涉及存档迁移与兼容处理。
4. 纯文档 PR 明确写「仅文档，无产品代码变更」。
5. PR 审核问题分级：P0 严重故障、P1 主要功能缺陷、影响演示主流程的问题必须修复；非阻塞 P2 登记 Issue，不阻挡合并；审核通过不等于合并授权。

## 5. 合并与同步 main

- 是否合并 PR 始终由用户决定；未经明确授权，任何代理或工具不得自行合并。
- 获得合并授权后按授权方式合并，再同步 `main`，从最新 `main` 开始下一阶段。
- 前置阶段未合并时，不得把依赖它的接口当作已有；需要并行时先固定公共契约并单独评审。
- 分支落后时先同步 `main` 再继续；冲突解决不得静默丢弃他人改动。

## 6. 权限与异常

- 文件写入、网络、GitHub 操作按当前会话权限执行；权限被拒绝时报告具体环节，不伪称成功。
- 指南缺失、不可读，或冲突涉及产品规则与公共契约取舍时：停止受影响部分，报告文件、差异与决定点；未受影响部分继续，纯表述不一致按 AGENTS 开头规则修正。
- 发现需求与已确认规则冲突时，优先采用用户最新明确方向；只有无法合理决定且会实质改变产品行为时才询问。
- 不得自行修改已确认的产品规则、评分机制或数值参数；发现问题应报告原因、影响与建议。

## 7. 最终汇报格式

完成任务后向用户汇报：

1. 实际修改/新增的文件；
2. 新旧方向差异（若为指南任务）；
3. 模块架构与依赖（若涉及架构）；
4. 保留的规范与删除/后置的旧规则；
5. 验证结果与未验证部分；
6. 分支名、Commit SHA、PR 链接；
7. 明确说明是否已合并（默认未合并）。
