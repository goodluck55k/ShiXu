# 分阶段开发路线

本文件规划后续开发，不表示功能已经完成。指南先在 `docs/development-guide` 完成并创建 PR，用户授权合入 main 后，产品分支才从新的 main 开始。不得在指南分支开发产品。

## 1. 顺序与依赖

| 阶段 / 分支 | 前置 | 本分支交付 | 一次最小完成检查 |
| --- | --- | --- | --- |
| G0 · docs/development-guide | 初始 main | 七份一致的开发指南、参考源码记录、待审核 PR | 一轮文档/链接/分支/文件差异检查，不跑产品测试 |
| P1 · feature/web-skeleton | G0 经授权合入 | Next.js App Router / TS / Tailwind、入口页面、domain 公共类型、StoragePort、本地 snapshot、输入与简单文本历史；手动 neutral 占位闭环 | 启动 → 保存一条 → 刷新仍在；一次相关类型/构建检查 |
| P2 · feature/emotion-analysis | P1 | /api/emotion、server-only provider、严格 schema、AI 结果确认、完整手选、保存前/后纠正、过期响应处理 | 一次正常确认与一次故障手选；纠正不重复奖励（本阶段奖励尚可为 0） |
| P3 · feature/character-layers | P2 | 原创全身 SVG 基底、五官/服饰/配件/特效分层、纯函数视觉映射、有限短动作、减少动态效果 | 初始全白 → 积极/消极两种可见状态；无真实 API 可用手选 |
| P4 · feature/growth-memories | P3 | rules-v1 经验/阶段/解锁、幂等、日上限、装饰隐藏恢复、回忆列表、已保存纠正的视觉处理 | 一条积极 → 一条消极 → 恢复 → 刷新；经验所有权不回退；重复提交不发双份 |
| P5 · feature/experience-polish | P4 | 手机/桌面布局、加载空态错误态、保存失败反馈、JSON 导出导入、演示说明与部署所需配置 | 一次完整主流程 + 无 API 路径；导入后能读回已导出存档 |
| P6（可选）· feature/companion-milestones | P5 | 规则自主行为、纪念品、回忆时间线、阶段叙事，按可用比赛时间选做 | 触发一个行为和一个里程碑，无离线惩罚，无模型动作权限 |

P1–P3 的临时 UI 或占位数据必须明确，P4 才接入完整养成规则；不得将阶段性 0 奖励占位宣称为最终玩法。后续分支复用既有类型，不另起一套情绪或角色模型。

## 2. 最小演示交付线

P1–P5 构成完整 MVP：文字记录 → AI 或手选 → 用户确认 → 规则状态更新 → SVG 反馈 → 成长/装饰回忆 → 本地恢复。比赛时间紧时优先这条主线；P6 不得阻塞前五阶段交付。

不将登录、云同步、语音、多模型 Agent、社交、3D、商业化作为当前前置。真实 Key 不可用可交付手选闭环和契约 mock，并如实注明真实 AI 未验通；后续配置服务端环境后仅补一次真实请求检查。

## 3. 分支任务卡约定

每阶段实施指令写明：目标、允许改动模块、依赖提交、公共接口、最小验收、暂不实现项。已有同任务分支或 PR 先检查再复用。不要一次启动后续全部功能分支，也不把未合入的接口假定为 main 已存在。

只有用户允许并完成前置合并后才进入下一阶段。跨阶段小缺口能在当前范围内用简化实现接上时直接完成并记录；需要改变产品方向或破坏契约时明确指出具体决定点。

## 4. 完成判据

当前任务功能完整、必要最小冒烟通过（或明确外部限制与可用降级）、提交推送成功、唯一任务 PR 已创建，视为可交付待审核；是否合并由用户决定。不要把新增测试数量、全面覆盖率和反复全量回归作为阶段完成门槛。
